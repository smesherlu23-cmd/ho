# Эксплуатация

Как установить Whatever на сервер, открыть по HTTPS, обновлять, делать резервные копии
и следить за работой. Все команды выполняются в папке репозитория на сервере.

## Из чего состоит

| Сервис | Образ | Что делает |
| --- | --- | --- |
| `frontend` | nginx без прав root | отдаёт приложение, проксирует `/api` и `/ws` на бэкенд; единственный сервис, доступный снаружи |
| `backend` | Python 3.12, uvicorn | API и синхронизация досок, один процесс; картинки и вложения досок — том `files-data` |
| `migrate` | тот же, что `backend` | применяет миграции базы и завершается; бэкенд стартует после него |
| `postgres` | PostgreSQL 16 | данные; том `postgres-data` |
| `backup` | PostgreSQL 16 | раз в сутки копирует базу и файлы досок в папку `backups/` |

У каждого долгоживущего сервиса есть healthcheck: `docker compose ps` показывает `healthy`,
когда сервис готов. nginx запускается только после того, как бэкенд стал здоровым,
а бэкенд — после успешных миграций.

## Требования

- Linux с Docker и плагином Compose v2.20 или новее.
- 2 ядра и 2 ГБ памяти хватает на 100 одновременных участников (см. «Нагрузка» ниже),
  плюс место на диске под базу, файлы досок и резервные копии.
- Открытый порт приложения (по умолчанию 8080) или внешний прокси с TLS перед ним.

## Установка

```bash
git clone https://github.com/smesherlu23-cmd/ho.git whatever && cd whatever
cp .env.example .env
nano .env                                   # задайте POSTGRES_PASSWORD
docker compose up -d --build --wait
docker compose exec backend python -m app.cli create-admin admin --name "Иван Иванов"
```

`--wait` дожидается, пока все сервисы станут здоровыми, и завершается ошибкой, если этого
не случилось. Пароль базы задаётся один раз: с ним PostgreSQL создаёт базу при первом запуске.

## Настройки

Все настройки — в `.env`, полный список с пояснениями — в [.env.example](../.env.example).
После изменения `.env` пересоздайте контейнеры: `docker compose up -d`.

Бэкенд проверяет настройки при запуске. Если значение неверное, контейнер не запустится,
а в `docker compose logs backend` будет указано, какая переменная и что с ней не так.

История версий досок хранится в базе. Версия — доска целиком, поэтому от настроек
`WHATEVER_VERSION_INTERVAL_MINUTES` (как часто сохраняется версия, пока доску меняют)
и `WHATEVER_VERSION_RETENTION_DAYS` (сколько дней хранятся безымянные версии) зависит,
как быстро растёт база. Названные версии хранятся, пока их не удалят.

## HTTPS

Приложение само TLS не завершает: перед ним ставят прокси с сертификатом. Готовая
настройка nginx на том же сервере — [ops/nginx/whatever.conf](../ops/nginx/whatever.conf):
сертификат Let's Encrypt к ней добавляет certbot, пошагово — в [deploy-vps.md](deploy-vps.md).
Своему прокси (Caddy, nginx с сертификатом компании) нужно то же, что в этом файле:

- передавать WebSocket (`Upgrade`, `Connection`) и держать соединение не меньше часа;
- не ограничивать размер тела запроса (`client_max_body_size 0`): размер файла проверяет
  приложение, а nginx по умолчанию отклоняет всё больше 1 МБ;
- передавать `Host` без изменений и добавлять `X-Forwarded-For`.

И в `.env`:

```bash
WHATEVER_COOKIE_SECURE=true                 # cookie входа только по HTTPS
WHATEVER_TRUSTED_PROXY=172.16.0.0/12        # адрес прокси, как его видит контейнер
WHATEVER_BIND_ADDRESS=127.0.0.1             # прокси на этом сервере: порт 8080 не открыт наружу
```

`WHATEVER_TRUSTED_PROXY` нужен защите от подбора пароля: она считает попытки по адресу
пользователя, а без этой настройки все пользователи будут выглядеть как адрес прокси.
Для прокси на том же сервере это подсеть Docker (`172.16.0.0/12`), для отдельного
сервера — его адрес. Указывайте только адрес своего прокси: тому, кому nginx доверяет,
он верит и в заголовке `X-Forwarded-For`.

Прокси должен передавать `Host` без изменений: бэкенд сверяет его с `Origin`, чтобы
отклонять запросы с чужих сайтов.

## Обновление

Что изменилось в каждой версии и нужно ли что-то делать при обновлении — в
[CHANGELOG.md](../CHANGELOG.md). Установленную версию показывают `/api/health`
и меню пользователя в интерфейсе.

**Готовые образы** (рекомендуется). К каждому релизу CI собирает образы и публикует их
в GitHub Container Registry, так что сервер ничего не собирает и получает ровно те образы,
что прошли проверки. Один раз добавьте в `.env`:

```bash
WHATEVER_IMAGE_PREFIX=ghcr.io/smesherlu23-cmd/whatever
```

и для каждого обновления укажите версию:

```bash
make backup                                 # копия перед обновлением
git fetch --tags && git checkout v0.3.0     # docker-compose.yml и скрипты этой версии
sed -i 's/^WHATEVER_VERSION=.*/WHATEVER_VERSION=0.3.0/' .env   # или впишите строку
docker compose pull
docker compose up -d --no-build --wait --remove-orphans
```

**Сервер без доступа в интернет.** На странице релиза на GitHub лежит архив
`whatever-<версия>-images.tar.gz` со всеми образами. Перенесите его на сервер и загрузите:
`docker load -i whatever-0.3.0-images.tar.gz`, дальше — как выше, без `docker compose pull`.

**Сборка на сервере** из исходников (без `WHATEVER_IMAGE_PREFIX` и `WHATEVER_VERSION`):

```bash
make backup
git pull
docker compose up -d --build --wait --remove-orphans
```

Миграции применяются автоматически: сервис `migrate` выполнит их до старта нового бэкенда.
Если миграция не удалась, бэкенд не запустится, а причина будет в `docker compose logs migrate`.
При остановке бэкенд дописывает в базу изменения открытых досок, на это отведено 30 секунд.

### Переход на версию с файлом .env

Раньше пароль базы передавался в команде запуска, а без него был `whatever`. Теперь
он задаётся в `.env` и обязателен. При обновлении такой установки:

1. Создайте `.env` из `.env.example` и укажите в `POSTGRES_PASSWORD` прежний пароль
   (`whatever`, если его не задавали). База уже создана с ним, и другой пароль она не примет.
2. Если пароль был `whatever`, смените его (см. ниже «Смена пароля базы»).
3. Запустите с `--remove-orphans`: это удалит контейнер Redis, который больше не нужен.

## Резервное копирование

Данные лежат в двух местах: в базе (доски, учётные записи, права) и в томе `files-data`
(картинки и вложения досок). Сервис `backup` каждый день копирует оба в папку `backups/`
рядом с `docker-compose.yml` и удаляет копии старше 14 дней. Сначала копируется база, потом
файлы: в копии есть все файлы, о которых знает база. Копия делается на работающем
приложении, останавливать его не нужно.

Каждая копия — два файла с общим именем:

```
backups/whatever-2026-11-23T0000.dump            база (pg_dump -Fc)
backups/whatever-2026-11-23T0000.files.tar.gz    файлы досок
```

Файлы копий доступны только root: в них хеши паролей и все доски. Папку, час (по UTC)
и срок хранения задают `WHATEVER_BACKUP_DIR`, `WHATEVER_BACKUP_HOUR` и
`WHATEVER_BACKUP_KEEP_DAYS` в `.env`. Результат каждой копии и ошибки —
в `docker compose logs backup`.

Копия вне расписания, например перед обновлением:

```bash
make backup
```

Храните копии не только на этом сервере: например, забирайте папку `backups/` на другой
сервер через `rsync` по cron.

### Восстановление

```bash
make restore BACKUP=whatever-2026-11-23T0000
```

Команда останавливает бэкенд, заменяет базу и файлы досок содержимым копии (файлы, которых
в копии нет, удаляются) и запускает бэкенд снова. Копию она ищет в папке копий; копию
с другого сервера сначала положите туда. CI на каждом изменении делает копию,
удаляет все данные и восстанавливает их из копии, так что этот путь проверен.

У участников, которые открывали доски после создания копии, в браузере остались более
новые версии этих досок. Когда они откроют доску снова, эти изменения вернутся на сервер:
так устроена работа без сети.

## Нагрузка

Нагрузочный тест подключает участников к доскам по WebSocket так же, как браузер, и
измеряет, через сколько изменение одного участника доходит до остальных:

```bash
LOAD_PASSWORD=... make load LOGIN=admin URL=http://whatever.example.local:8080
```

Учётная запись нужна любая; тест создаёт свои доски и удаляет их в конце. Параметры
(`ARGS="--clients 50 --duration 120"`) — в `uv run python -m scripts.load --help`.
Тест завершается с ошибкой, если хоть одно изменение не дошло, сервер оборвал подключение
или p95 задержки больше 200 мс. Ресурсы сервера во время теста — в `docker stats`.

Результат на 4 ядрах, тест на той же машине (2026-11-23): 100 участников на 5 досках,
минуту каждый двигает курсор 10 раз в секунду и раз в секунду меняет доску. Это тяжелее
живой работы: люди не двигают курсор непрерывно все сразу.

| Что | Значение |
| --- | --- |
| Изменений | 5 800 отправлено, все 110 200 доставок дошли |
| Задержка изменения | p50 36 мс, p95 140 мс, p99 190 мс |
| Присутствие | 980 сообщений в секунду от участников, 18 600 в секунду разослано |
| Оборванных подключений | 0 |
| Бэкенд | 80–108 % одного ядра, 85–97 МБ памяти |
| nginx, PostgreSQL | 37 % ядра; до 6 % ядра |

Задержки завышены: тест сам занимал те же ядра, и его цикл событий опаздывал до 43 мс.
Бэкенд — один процесс, поэтому упирается в одно ядро: при такой нагрузке запас небольшой.
Почти всё время занимает рассылка присутствия, а не изменения досок. Если участников
станет заметно больше, следующий шаг — реже рассылать курсоры (склеивать их на сервере),
а не добавлять процессы.

## Журналы и наблюдение

```bash
docker compose ps                           # состояние и здоровье сервисов
docker compose logs -f backend              # журнал бэкенда
curl -s http://localhost:8080/api/health    # 200 — всё в порядке, 503 — база недоступна
```

Журналы контейнеров ограничены: до 5 файлов по 10 МБ на сервис. Для сборщиков журналов
(Loki, ELK, Vector) включите `WHATEVER_LOG_FORMAT=json`: каждая запись станет одной строкой
JSON с временем в UTC. Успешные проверки здоровья в журнал доступа не пишутся.

У каждого запроса есть id: nginx передаёт его бэкенду, бэкенд пишет его в каждую запись
журнала, сделанную во время запроса (`[3f2a…]` в тексте, поле `request_id` в JSON),
и возвращает в заголовке ответа `X-Request-ID`. Если пользователь сообщил об ошибке и
прислал этот заголовок из инструментов разработчика, запрос находится одной командой:
`docker compose logs backend | grep <id>`.

### Показатели для Prometheus

Бэкенд отдаёт показатели в формате Prometheus на `/api/metrics`, если в `.env` задан
токен `WHATEVER_METRICS_TOKEN` (без него адрес отвечает 404):

```yaml
scrape_configs:
  - job_name: whatever
    scheme: https
    authorization:
      credentials: <WHATEVER_METRICS_TOKEN>
    static_configs:
      - targets: ["whatever.example.local"]
    metrics_path: /api/metrics
```

| Показатель | Что значит |
| --- | --- |
| `whatever_rooms_open`, `whatever_connections` | открытые доски и подключения к ним |
| `whatever_http_request_duration_seconds` | время ответа API по методу, шаблону пути и коду |
| `whatever_board_saves_total{result}`, `whatever_board_save_duration_seconds` | записи изменений досок в базу и их время; рост `result="error"` — проблемы с базой |
| `whatever_board_compactions_total` | сжатия истории досок |
| `whatever_slow_client_disconnects_total` | участники, отключённые за отставание |
| `whatever_presence_dropped_total` | отброшенные сообщения присутствия (слишком частые или большие) |
| `process_*`, `python_gc_*` | память, процессор и сборка мусора процесса бэкенда |

## Смена пароля базы

```bash
docker compose exec postgres psql -U whatever -d whatever -c '\password whatever'
```

Затем укажите новый пароль в `POSTGRES_PASSWORD` в `.env` и перезапустите: `docker compose up -d`.

## Ограничения

Бэкенд работает одним процессом: комнаты досок живут в его памяти. Запускать несколько
копий бэкенда нельзя, пока комнаты не начнут обмениваться изменениями через Redis
(см. [ARCHITECTURE.md](../ARCHITECTURE.md)).
